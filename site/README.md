# Docs site

The docs site at <https://odonckers.github.io/domestic-ui/>, the root `README.md`, `llms.txt` and
`llms-full.txt` are all generated by one zero-dependency Node script from the sources that already
document the system: `PRINCIPLES.md`, the header comments in `css/`, the pages in `examples/`, and
a few handwritten files in `site/content/`.

```sh
node site/build.mjs           # build _site/ and write README.md, llms.txt, llms-full.txt
node site/build.mjs --check   # exit 1 if README.md, llms.txt or llms-full.txt are stale
```

## Preview

```sh
node site/build.mjs && node scripts/serve.mjs
```

Then open <http://127.0.0.1:4173/_site/index.html>. `scripts/serve.mjs` does not resolve directory
indexes, which is why every docs link points at a file (`principles/index.html`, never `principles/`).

## How the build works

| File | Does |
| --- | --- |
| `site/build.mjs` | Entry point and CLI. `generate(root)` builds everything in memory; `build({ root, outDir, writeRoot })` writes it; `stale(root)` powers `--check`. |
| `site/lib/discovery.mjs` | Reads the repository into one model: principles, token files, components, examples, demos, overrides, snippets. |
| `site/lib/css-comments.mjs` | Parses CSS header comments and the `@layer` order. |
| `site/lib/tokens.mjs` | Parses every file in `css/tokens/`, resolves light and dark values, picks a preview kind (see [Tokens](#tokens)). |
| `site/lib/markdown.mjs` | A small Markdown to HTML converter (the subset `PRINCIPLES.md` and `site/content/` use). |
| `site/lib/nav.mjs` | The Docs sidebar: its fixed entries and how pages are listed under them (see [Sidebar](#sidebar)). |
| `site/lib/pages.mjs` | Defines every page as blocks of Markdown, or custom HTML plus its Markdown equivalent. |
| `site/lib/templates.mjs` | The HTML page frame (skip link, header, sidebar, main, footer) and the Markdown twin. |
| `site/lib/outputs.mjs` | `README.md`, `llms.txt`, `llms-full.txt` and `_site/search-index.json`. |
| `site/lib/live.mjs` | Render pages (`live/`) and the redirects at old example URLs (see [Render pages and redirects](#render-pages-and-redirects)). |
| `site/lib/other-systems.mjs` | Validates `site/data/other-systems.json` and adds its section to each page (see [How other systems do it](#how-other-systems-do-it)). |
| `site/check-other-systems.mjs` | Dead-link check for that file; run by `npm test`. |
| `site/assets/site.css` | Docs layout only, with semantic `--dui-*` tokens and the layout primitives. |
| `site/assets/site.js` | Progressive enhancement only: closes the Docs menu on narrow screens, runs the token filter. |

`_site/` is wiped and rebuilt each time. `css/` and `web-components/` are copied into it unchanged,
so the docs and the render pages load the real CSS and components by relative path, at `/_site/`
locally and at `/domestic-ui/` on GitHub Pages. `examples/` is not published: its snippets are, each
on one docs page. Every HTML page gets a Markdown twin next to it (`tokens/semantic.md` beside
`tokens/semantic.html`). Output is deterministic (sorted inputs, no timestamps), so `--check` can
compare bytes.

`_site/search-index.json` has one record per page (`title`, `url`, `level` = its sidebar entry,
`summary`, and its `h2`/`h3` `headings`) for a later in-page search. There is no search UI yet.

## Page structure

Element, component, layout and pattern pages follow the order of an MDN reference page. A new page
type follows it too:

1. **H1 and a one-sentence summary.** An **Our choice:** line under it only when no native element
   or APG pattern covers the thing.
2. **Live example.** Per snippet: its name (`###`), its render and directly below it its markup,
   from the same text (see [Snippet convention](#snippet-convention)). Prose never repeats markup.
   Planned patterns show "Coming in M3." instead and nothing else from this list until 4.
3. **Attributes** (**API** for layouts and utilities). The `data-<component>` attribute and its
   values, the native attributes that matter, then short usage notes. Labelled header blocks
   (`States`, `Sizes`, `Focus`), `Keyboard` and the group README's **Our choice** bullets follow.
4. **Accessibility.** Short, concrete bullets, each borrowed fact linked to WCAG, APG, MDN or its author.
5. **Specifications.** Labelled links: MDN, WHATWG, W3C, WCAG 2.2, WAI-ARIA APG.
6. **See also.** The level index, the component API convention, the accessibility baseline, and the
   source files on GitHub.
7. **How other systems do it**, last (see below).

Writing rules: be specific and direct; no preamble ("This page describes…"), no repeating the
summary in the body, no marketing. Never present a native pattern as ours. One short example per
concept. Opinion only as **Our choice:** with one line on why. Link every borrowed fact to its source,
or drop it.

## Sidebar

Every page has one navigation: the Docs sidebar, `<nav aria-label="Docs">`. Its top-level entries
are fixed in `NAV` in `site/lib/nav.mjs`, in this order; each links its index page and lists the
pages of its sections below it, in the order `buildPages()` returns them.

| Entry | Links | Lists |
| --- | --- | --- |
| Getting started | `index.html` | |
| Principles | `principles/index.html` | one page per `PRINCIPLES.md` section |
| Tokens | `tokens/index.html` | one page per file in `css/tokens/` |
| Base | `components/base.html` | utilities (`components/utilities/<name>.html`) |
| Layout | `layouts/index.html` | the layout primitives |
| Atoms, Molecules, Organisms | `<group>/index.html` | `components/<group>/<name>.html` |
| Patterns and guides | `patterns/index.html` | every pattern with "(coming in M3)" while planned, `guides/index.html`, every guide |
| Demos | `demos.html` | |
| Contributing | `contributing.html` | |
| Changelog | `changelog.html` | |

**Our choice:** utilities sit under Base, not Layout, because they are not layout primitives.
There is no examples section: each example is on its element's page, and the old example URLs
redirect there.

A new page goes where its `section` says (`Page["section"]` in `site/lib/pages.mjs`); there is no
per-page nav to edit. The current page's link has `aria-current="page"` (exactly one per page); its
entry's `<li>` gets `data-current-section`, drawn as a tinted band with an edge line, with no
second `aria-current`. The build fails if an entry links a page that is not built.

The sidebar is a native `<details open>` with the summary "Docs menu". Without JavaScript it is open
at every width. `site.js` closes it on load when the viewport is narrower than `64em` and keeps it
open when wider (the same query as `site.css`). At `64em` and up the body is a CSS grid with the
sidebar column (`--dui-size-column-min`) beside `main`; the sidebar is sticky, at most one viewport
tall and scrolls on its own; the summary is hidden while the menu is open. Links and the summary
are at least 44px tall (`--dui-size-target`).

`llms.txt` has one H2 per sidebar entry, in the same order. `README.md` is short: the intro, links,
install and use, the principles list, one components table (Base, Layout and the component levels),
the patterns table, demos, contributing and license. `llms-full.txt` has every reference page; pages
built with `inFull: false` (`Page` in `site/lib/pages.mjs`) are only linked from `llms.txt`: the
demos, patterns and guides indexes, the tokens and layouts indexes, level indexes with no group
README, guides, Contributing and Changelog. A block with `inFull: false` (`Block`) is on the page and
its twin but not in `llms-full.txt`, so nothing is there twice: a level index's list of pages (each
page's summary opens its own part) and a component's **Our choice** bullets (all of them are on the
level index).

## Component API convention

Each component exposes one `data-<component>` attribute whose value is space-separated words
matched with `~=` (like `rel`), for example `data-button="primary small"`. Component APIs use no
classes; state is carried by native attributes and ARIA (`disabled`, `aria-disabled`, `aria-busy`,
`aria-invalid`). Layout primitives and utilities are classes (`.stack`, `.cluster`, `.grid`,
`.visually-hidden`), or one attribute where the API block names no class (`data-scroll`). The build
states this on `index.html` (with the **Our choice:** why, taken from the group README's bullet
about `data-<…>`), in `README.md`, `llms.txt` and `llms-full.txt`; component pages link it under
See also.

Layout directories are all read, in the order above; when two hold a file of the same name, the
first wins. Missing directories are skipped.

Relative links in `PRINCIPLES.md` and override bodies are repo-root paths. They are rewritten to the
matching docs page where one exists (`examples/theming.html`, `css/layout/stack.css`, a
`PRINCIPLES.md#heading` anchor), and to `https://github.com/odonckers/domestic-ui/blob/main/<path>`
otherwise.

## Adding a component (M2, M3)

No site change is needed. Add the files below and run `node site/build.mjs`:

- `css/components/<group>/<name>.css`, with `<group>` one of `atoms`, `molecules`, `organisms`.
- `examples/<group>/<name>.html`, a standalone valid page, joined to the CSS by file name, with each
  demo in a named snippet region (see [Snippet convention](#snippet-convention)). Optional: without
  it the page says there is no live example yet. `examples/<group>/index.html` is a showcase, not a
  component: a test fixture with no snippets, whose URL redirects to the level index.
- A row in the index table of `css/components/<group>/README.md`, if the group has one. A CSS file
  missing from the table still gets a page (from its header comment alone), so nothing is dropped.
- An entry in `site/data/other-systems.json` (see [How other systems do it](#how-other-systems-do-it)).
  Without one the page builds, and the build prints a warning naming it.

### Group README

When `css/components/<group>/README.md` has a table whose second and third columns are `File` and
`API`, it is the source of truth for that group: one page per row, in row order.

| Column | Used as |
| --- | --- |
| 1, name | The page title ("Buttons"). |
| `File` | The CSS file, a link relative to the README. A cell starting with `none`, such as ``none: [`css/base/forms.css`](../../base/forms.css)``, means the row has no CSS file of its own: it still gets a page, named after its example file, and the linked file is shown as its source. |
| `API` | Shown as written (inline Markdown, `\|` unescaped) above the header's `API` block, and in the `README.md` index's API column. Its attribute names (`data-button`, `aria-disabled`, `role`) select the Our choices bullets for the page. |
| `Example` | The example page whose snippets are the live example. |
| `Specs` | Spec links, before any header-comment URL they do not repeat. A label that is only a number ("3.3.2") gets its host label ("WCAG 3.3.2"). |

The "Our choices" bullets appear, labels intact, on `<group>/index.html`.
A bullet also appears on a component page under "Our choice" when one of its code spans uses an
attribute from the row's API cell, or its text names the row's title (singular or plural). The
bullet about `data-<…>` is the convention itself and is shown with the component API convention
instead. The "Not shipped, and why" table appears as a table on both index pages. A row whose file
does not exist fails the build.

If the name matches a registered pattern (see [Patterns](#patterns)), the files fill in that
pattern page instead. The "coming in …" note for a group disappears from `<group>/index.html`
and `README.md` as soon as the group has one CSS file or one available pattern.

A layout primitive works the same way: add `<name>.css` to `css/layout/`, `css/layouts/` or
`css/components/layouts/`, and optionally `examples/layout/<name>.html` or
`examples/layouts/<name>.html`.

### Header comment fields

The parser reads the comment that opens the CSS file:

```css
/*
 * Atom: button
 *
 * The native button element, styled by type. More prose becomes notes.
 * Sentences that mention WCAG, ARIA, focus, contrast or accessibility
 * become the accessibility notes.
 *
 * API
 *   class="button"
 *   --button-gap   space between icon and label (default: var(--dui-space-xs))
 *
 * Example
 *   <button type="button" class="button">Save</button>
 *
 * https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button
 * https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
 */
```

| Field | Rule |
| --- | --- |
| Label | An optional first paragraph of one line in the form `Word: text` (`Atom: button variants, sizes and states`); never the summary. |
| Summary | The example page's `<meta name="description">`, else the first sentence of the first prose paragraph. Plain text: it is also the meta description. |
| Notes | The prose paragraphs, less the summary sentence when the summary came from the comment, less sentences repeated under Accessibility, with URLs removed (they are listed under Specifications). Shown at the end of Attributes. |
| `API` | A paragraph whose first line is `API`; the indented lines below it, dedented. `API: …` one-liners in any comment are collected too. |
| `Example` | A paragraph whose first line is `Example`. Not shown: example markup comes only from snippets in `examples/`. |
| `Keyboard` | A paragraph whose first line is `Keyboard`; `Key: action` lines, shown as a Keyboard table. |
| Other labelled blocks | A paragraph whose first line is one capitalized word (`States`) over indented lines, or that opens with `Word: ` (`Sizes: default and large are …`). Shown verbatim as preformatted text under a heading of that word, without the label. |
| Accessibility | Prose sentences that mention WCAG, ARIA, APG, focus, contrast, accessibility, screen readers, forced colors or reduced motion, one bullet each, URLs removed. With none, one bullet says there is nothing beyond the accessibility baseline. |
| Specs | Every URL in the comment, labelled by host (MDN, WHATWG, WCAG for `/WAI/WCAG22/Understanding/` and `/TR/WCAG…`, APG for `/WAI/ARIA/apg`, W3C for other `w3.org` and `csswg.org`, else the site's name) and the page it names (`specName()`: "MDN `gap`", "WCAG Use of color"). |

The title is the file name: `visually-hidden.css` becomes "Visually hidden".

### Front matter overrides

To override what the comment gives, add `site/content/components/<group>/<name>.md`
(`site/content/components/base.md` for base elements):

```md
---
title: Button
summary: One line.
specs:
  - MDN <button>: https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button
our-choice: One line on why, only when no native element or APG pattern covers it.
usage:
  - One usage note per item, Markdown. `usage: none` drops the comment's notes.
---
- Markdown body = accessibility bullets, each fact linked to its source.
```

Only `key: value` pairs and `- item` lists are parsed. Each key is optional; anything left out falls
back to the header comment. A `specs` entry is `Label: URL`. `usage` replaces the derived notes and
is shown as a list at the end of Attributes. The body replaces the derived accessibility notes; its
relative links are repo-root paths, rewritten as above. Layout overrides live at
`site/content/components/layouts/<name>.md`, whichever CSS directory the layout is in. The atoms
and `scroll` have overrides because their comments mix usage, accessibility and URLs in one paragraph.

`our-choice` is rendered under the summary as "**Our choice:** …". Use it only where no native
element and no [WAI-ARIA APG pattern](https://www.w3.org/WAI/ARIA/apg/patterns/) exists; where one
does, link it under `specs` instead and never present it as ours.

## Patterns

`site/content/patterns/<slug>.md` is the registry of planned patterns, one file each. The body
is optional: Markdown accessibility bullets, shown under Accessibility once the pattern is available
in place of the sentences derived from the CSS header. CSS header URLs the body already links are
not repeated under Specifications. The front matter is the data:

```md
---
title: Tabs
summary: Sections of content shown one at a time, chosen from a list of tabs.
milestone: M3
level: molecule
standard: APG Tabs pattern: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/
specs:
  - Label: https://…
sources:
  - tabs
keyboard:
  - Tab: moves focus into the tab list, onto the active tab.
  - Left Arrow / Right Arrow: moves focus to the previous or next tab.
---
```

| Key | Rule |
| --- | --- |
| `title`, `summary` | Required in practice. Inline Markdown. |
| `milestone` | `M3` or `M3b`; groups `patterns/index.html` and sets the "Coming in …" sentence. |
| `level` | `molecule`, `organism`, `layout` or `token`; places the pattern on that level's index page (`molecules/index.html`, `layouts/index.html`, …). |
| `standard` | One `Label: URL` or a list of them: the native element or APG pattern it follows. |
| `our-choice` | One line, only when there is no standard. The build fails if a pattern has neither. |
| `specs` | Further `Label: URL` links, shown under Specifications after the standards. |
| `sources` | Other file names that fill this pattern in (`dialog.md` lists `dialog` and `drawer`). The slug is always one. |
| `keyboard` | `Key: action` lines, used only when neither the example nor the CSS has a `Keyboard` block. Separate alternative keys with ` / `. |

A pattern **fills in on its own** when any of its names matches a file:

- an example page `examples/{molecules,organisms,layouts,layout,patterns}/<name>.html`, or
- a CSS file `css/**/<name>.css` (outside `css/base/` and `css/reset/`).

A pattern owns its names: `css/components/molecules/tabs.css` fills `patterns/tabs.html` and gets no
`components/molecules/tabs.html` page. A filled page follows [Page structure](#page-structure): live
example (the snippet convention below), Attributes (the
CSS header's API block), Accessibility, Keyboard, Specifications (standards, `specs`, then CSS header
URLs), See also with the source files. Keyboard notes come from the first `Keyboard`
block found in an HTML comment of the example page, else in the CSS header comment, else the
`keyboard` front matter; with none, one line points at the standard's keyboard section.

```css
/*
 * Keyboard
 *   Left Arrow / Right Arrow: moves focus to the previous or next tab
 *   Home  moves focus to the first tab
 */
```

Until a file lands, the page shows only the summary, the Our choice line if any, "Coming in M3."
(or M3b), Specifications (the standards and `specs`) and See also: no demo, no markup, no keyboard
table. `README.md` lists every pattern with its
status and adds available ones to the components table at their level; `llms.txt` links available
patterns to their `.md` twin and names planned ones with their milestone.

## How other systems do it

Base, component and pattern pages end with links to how Apple, Material and Geist handle the same
thing, from `site/data/other-systems.json`. Planned pattern pages have them too. The section is the
last on the page, after Specifications and See also, in the HTML page, its Markdown twin and
`llms-full.txt`; not in `llms.txt` or `README.md`.

Rules:

- **Comparison only.** The section opens with "For comparison only; these are not the standard this
  system follows." The standards a page follows are its spec links.
- **Links only.** Never copy text, descriptions, images or visuals from those systems. A link's label
  is the system name and the page title from the data file, nothing else.
- **`null` means "No equivalent".** Use it when the system has no page for the same thing; every
  entry lists all three systems.
- **Plain links**, no `target="_blank"`.

Format:

```json
{
  "systems": {
    "apple": { "name": "Apple Human Interface Guidelines", "home": "https://…" },
    "material": { "name": "Material Design 3", "home": "https://…" },
    "geist": { "name": "Vercel Geist", "home": "https://…", "soft404Title": "Geist Design System" }
  },
  "pages": {
    "patterns/tabs": {
      "apple": { "url": "https://…", "title": "Tab views" },
      "material": { "url": "https://…", "title": "Tabs" },
      "geist": null
    },
    "components/atoms/controls": {
      "apple": [{ "url": "https://…", "title": "Text fields" }, { "url": "https://…", "title": "Toggles" }],
      "material": null,
      "geist": null
    }
  }
}
```

- `systems`: exactly `apple`, `material` and `geist` (listed in that order on each page), each with a
  display `name`, an optional `home` page and an optional `soft404Title`.
- `pages`: keyed by site page path without `.html` (`components/base`, `components/atoms/button`,
  `patterns/tabs`). Each value has all three systems, each `null`, one `{ "url", "title" }` with an
  `https` URL and the page's title as that system writes it, or a non-empty list of those when one of
  our pages covers several of theirs (form controls: text fields, checkboxes, radios, switches,
  selects, sliders). Each link in a list is its own list item on the page and in llms-full.txt, in
  the order written; the link check checks every one.
- `soft404Title`: some sites answer 200 for pages that do not exist (Geist does, with a generic
  `<title>`). The link check fetches that system's page URLs with GET and fails any whose `<title>` is
  exactly this.

The build fails, naming each problem, when a key is not a built page, a system is unknown or missing,
or a value is not `null` or `{ url, title }` with an `https` URL. It prints a warning (and still
builds) for each base, component or pattern page with no entry.

To add an entry when an M3 component or pattern lands: add its key under `pages` with all three
systems, check each URL in a browser and copy only the page title, then run `node site/build.mjs`
(no warning left) and `node site/check-other-systems.mjs`.

### Link check

`node site/check-other-systems.mjs` requests every unique URL (pages and homes), redirects followed,
HEAD first and GET when HEAD answers 405, 501 or any 4xx/5xx other than 404 and 410. It prints one
row per URL and exits 1 on any failure:

| Final response | Result |
| --- | --- |
| 2xx | ok, unless the system's `soft404Title` matches (failure: soft 404) |
| 404, 410, any other 4xx | failure |
| 403, 429, 5xx | warning: bot walls and rate limits do not prove a page is gone |
| Timeout or network error, after one retry | warning |

`tests/docs-other-systems.spec.js` runs it in `npm test` (Chromium project only): failures fail the
test, warnings are printed and attached as annotations. The same spec tests each rule against a
local server.

## Tokens

`site/lib/tokens.mjs` reads every file in `css/tokens/` (found by listing the directory, sorted),
one page each. It reads the plain style those files use: one declaration per line (or continued
until `;`), selectors that may span lines.

| Source | Becomes |
| --- | --- |
| The file's header comment, first paragraph `Semantic tokens (public theming API).` | Page title "Semantic tokens", tier "public theming API" shown first in bold |
| The rest of the header comment | The page intro |
| A comment before a top-level rule (`/* 2. Dependent tokens: … */`) | A group, name before the colon, note after it |
| A comment inside a rule after a blank line or `{` (`/* Space */`) | A group; the nearest one above a declaration is its group |
| `--x: 1rem; /* text */` (trailing, same line) | The description of `--x` |
| A comment directly after a declaration line and directly above the next one, or directly under a group comment | The description of that next declaration |
| A declaration inside `@media`, `@supports` or any at-rule, or in a rule whose selector has no `:root` | A condition on the token of that name: "With `@media (…)`: value, resolves to …" in its description, never a light or dark value |

So to describe a token, put a comment on its line or on the line above it with no blank line in
between. A token with no comment falls back to its purpose in the `PRINCIPLES.md` semantic token
table, marked "†" (the page intro says where † descriptions come from); with neither it shows
"No description yet" in muted italic.

Values: **Written as** is the value in the file. **Light** and **Dark** substitute every `var()`
recursively through the tokens of all files (a fallback is used for unknown names; a cycle stays as
written) and take the first or second argument of `light-dark()`. Other functions (`color-mix()`,
`clamp()`) are left as written with their arguments resolved.

Previews, by name then value (`previewKind()`): color (`-color-`, or a color value) as a swatch;
`-shadow-` as a shadowed box; `-space-`, `-size-`, `--*-measure` lengths as a bar capped at half a
sidebar column; font family, size, weight, line height (`-leading-`) and letter spacing (`-tracking-`)
as "Aa"; `-radius-` as a rounded box; border and focus widths as a bordered box; anything else
(durations, easings, opacity, mix amounts, underline metrics) as "None", never animated. Previews
are decorative (`aria-hidden`): the Light and Dark cells of the same row hold the values as text, so
color is never the only cue. Light and dark samples sit one after the other (always both for colors,
one when the values match), each in a `data-color-scheme` scope. The sample's value is the resolved
literal (in `style="--preview: …"`), so the dark sample shows the dark value whatever the page
scheme. A value that would need an HTML entity in the `style` attribute gets "None".

Each group is a `<table>` with a `<caption>` ("Spacing (primitive tokens)"), `<th scope="col">`
headers and the token name in `<code>` in a `<th scope="row">`, wrapped in:

```html
<div data-scroll="inline" tabindex="0" role="region" aria-label="Spacing (primitive tokens) (scrolls horizontally)">
```

`data-scroll="inline"` is the core CSS API for horizontal scroll regions, styled by
[`css/layout/scroll.css`](../css/layout/scroll.css); `site.css` adds no rule of its own. Tables are never `display: block`. Hyphenated words in values never
break, so a narrow table scrolls in its region instead of breaking names apart. The wrapper is a
`div` with `role="region"` by design, so the build adds an html-validate directive that silences
`prefer-native-element` for it.

The filter is a `<search>` with a `<label>` and `<input type="search">` ("Filter tokens"), `hidden`
in the HTML. `site.js` removes `hidden`, hides rows whose text (name, values, description, preview
value) does not contain the query, hides groups with no visible row, and writes "N tokens shown"
to a polite `role="status"` region after typing pauses. Without JavaScript every token shows and the
filter stays hidden. No requests leave the page.

The Markdown twins and `llms-full.txt` have the same tables as `| Token | Light | Dark | Description |`.

`site/content/guides/<slug>.md` (front matter `title`, `summary`; Markdown body with `site:` links
or repo-root links) becomes `guides/<slug>.html`. Two lines are generated at build time, so a

| Line | Becomes |
| --- | --- |

## Snippet convention

**Owner decision: one home per element.** Each element and pattern has one docs page, holding its
explanation and its live example. Example markup has one source: named snippet regions in
`examples/`. The build renders each snippet live on its page and prints its code from the same text.

```html
<div class="demo">
  <!-- dui:snippet name="Variants" -->
  <div class="cluster">
    <button type="button" data-button="primary">Primary</button>
  </div>
  <!-- /dui:snippet -->
</div>
```

- **One rule.** A snippet is the text between `<!-- dui:snippet name="…" -->` and
  `<!-- /dui:snippet -->`. `name` is required (the build fails without one), is the snippet's
  heading, and is unique in its file. Nothing else is a snippet: not `<pre><code>`, not `<main>`.
- **No copies.** Never add a `<pre><code>` copy of a demo; the docs print the region itself. A
  `<pre>` outside a region fails `tests/docs.spec.js` (a `<pre>` demo goes inside one).
- **Which page.** A snippet goes on the page of the component or pattern its example belongs to
  (`examples/atoms/button.html` → Buttons). `page="layouts/stack"` (a site path without `.html`) sends
  it elsewhere: `examples/base.html` uses it for the layout primitives and the utility,
  `examples/theming.html` for `principles/theming`. A snippet with no page fails the build.
- **One home.** Mark a demo only on its element's own page. `examples/base.html` keeps its forms,
  dialog and details demos unmarked: their pages are Form controls, Dialog and Disclosure.
- **Head snippets.** A region inside `<head>` (a theme's `<style>`) has no render of its own. It is
  printed right after the first render of its example, and every render of that example loads it.
- **Showcases** (`examples/<group>/index.html`) have no snippets; they are test fixtures.

The text is used verbatim, never reformatted. Two things are removed: the line break right after the
opening marker and the whitespace-only last line before the closing one; and the common leading
whitespace (the smallest indentation of the non-blank lines, from every line). So a snippet is always
the source slice with that indentation removed line by line.

On the page: `## Live example`, then per snippet its name (`###`), its render (an iframe of its
render page) and directly below, `<pre data-snippet>` with the code. The Markdown twin and
`llms-full.txt` have the name and a fenced block of the same text, with a fence longer than any
backtick run inside. `tests/docs.spec.js` checks that every snippet is printed and rendered on exactly
one page, byte for byte with the example, its render page, the twin and `llms-full.txt`, and that no
prose repeats a line of it.

## Render pages and redirects

`site/lib/live.mjs` writes pages that are not docs pages: not in the sidebar, the search index or the
llms files.

| Output | Is |
| --- | --- |
| `live/<example path>--<snippet name slug>.html` | One per snippet, the source of its iframe: the example's `<head>` (its CSS, page styles and theme), the snippet's text as the body, then the example's scripts after `</main>`. It sits at the example's directory depth, so the example's relative URLs work unchanged. `noindex`. |
| `examples.html`, `examples.md`, `examples/**/*.html` | The old example URLs. GitHub Pages has no server redirects, so each is a static page: `<meta http-equiv="refresh" content="0; url=…">` (no delay, which [WCAG 2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) allows), `<link rel="canonical">`, `noindex`, a title and a plain link. An example goes to the page that shows its snippets, a showcase to its level index, `examples.html` to Getting started. |

So that a snippet works alone in its render page:

- Links inside a snippet point in-page (`#…`), not at other example files.
- Example scripts tolerate a page that holds one snippet: `document.getElementById("save-demo")?.…`.

Frames are `14rem` tall without JavaScript, and at least `28rem` (`data-tall`) when the snippet opens
a dialog, popover, menu, toast or tooltip; `site.js` fits each frame to its content.

## Stale check

`README.md`, `llms.txt` and `llms-full.txt` are committed. Edit their sources, never the files
themselves, then run `node site/build.mjs`. Two checks catch a forgotten rebuild:

- `npm test` runs `tests/docs.spec.js`, which compares freshly generated content with the committed
  files byte for byte.
- The Pages workflow runs `node site/build.mjs --check` before building.

## Accessibility of the docs

Every page has a skip link (the first focusable element), one labelled Docs nav with one
`aria-current="page"`, one `h1`, tables with `<caption>` and `th scope`, and iframes with a `title`.
Code blocks wrap instead of scrolling horizontally, so no `<pre>` needs `tabindex` or an accessible
name (which ARIA 1.2 prohibits on the `pre` element's generic role). Long words, URLs and inline
code in prose break anywhere (`overflow-wrap: anywhere`); only token tables scroll, inside their
named `data-scroll` region.

`tests/docs.spec.js` (Chromium) runs html-validate and axe (WCAG 2.2 AA tags, light and dark) on
every page and every render page, blocks external requests, and checks the sidebar (one nav, order,
every built page reachable, one `aria-current`, no example links), the snippets (see
[Snippet convention](#snippet-convention)), the redirects (html-validate, axe, landing on their page),
the web components working in their frames, the token tables and parser, the filter, and the page
with JavaScript off.

`tests/docs-mobile.spec.js` runs in every Playwright project (Chromium, Firefox, WebKit). For every
built docs page (every `.html` in `_site/` outside `css/`, `web-components/`, `live/` and the
redirects), at 320×640 and 375×812, it
asserts `scrollWidth <= clientWidth` on the root (the failure names the widest element) and that no
`<pre>` scrolls, and runs axe with the same tags as `tests/a11y.spec.js`. Frames are excluded from
that axe run: their markup is `examples/` markup, checked by `tests/a11y.spec.js`. It also
opens and closes the Docs menu with Enter and Space at 375px, tabs to the current page link, and
checks the wide-screen sidebar. Both specs share `tests/docs-helpers.js`, which builds `_site/` once.
